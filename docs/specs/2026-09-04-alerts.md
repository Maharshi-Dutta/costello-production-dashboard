# Job alerts by email (spec, approved by the user 2026-09-04)

## Product context
Costello Windows runs its factory from one SharePoint workbook (`Production` sheet).
This dashboard (`d:\Costello Windows\Excel Dashboard\web`, static site, plain ES2017
browser JS, no bundler, no modules; `index.html`, `app.js`, `parser.js`, `graph.js`,
`checkpoints.js`, vendored MSAL + ExcelJS) reads the workbook by downloading it and
writes surgically through the Microsoft Graph Excel API. The GitHub repo is PUBLIC.

The feature: a person subscribes an email address to a job from the dashboard; every
third day at 08:00 Irish time one email per address goes out listing all of that
address's jobs with their comments. The mail is sent by a Power Automate flow inside the
tenant that runs an Office Script over the workbook; the dashboard only manages
subscriptions.

User's answers (binding):
1. Sender: the admin's own mailbox (the flow runs under the admin's account).
2. Schedule: every 3rd day at 08:00 Europe/Dublin.
3. Email content: just the job number and its comments. Nothing else per job.
4. A finished job is never emailed (finished = no longer in the "In production"
   section, or no longer on the Production sheet). No notice, it just stops.
5. Only the admin can add or remove subscriptions. Everyone can see them.
6. Office Scripts is available in the tenant (Automate tab present in Excel on the web).

## HARD RULES (security - non-negotiable)
- **No email address, no person's name, no domain name may appear anywhere in the
  repository**: not in code, comments, tests, fixtures, docs, screenshots or commit
  messages. Tests use obviously fake values like `admin@example.test`. The admin
  address and the allowed domain are READ AT RUNTIME from the workbook (below).
- Subscriptions live only in the workbook (sheet `Dashboard Alerts`), never in
  localStorage beyond the 180 s optimistic hold, never in the URL, never logged to
  the console.
- The dashboard refuses any address whose domain differs from the admin's domain
  (`admin.split("@")[1]`, compared lower-case). No address literal or domain literal in
  code.
- Nothing on the `Production` sheet or any other existing sheet is written by this
  feature. Only `Dashboard Alerts` and `Dashboard Log`. The `Dashboard Config` sheet is
  read-only for the dashboard.
- Offline tests only (fake fetch as in `test_move.js` / `test_checkpoints.js`). No
  network, no Graph, no `rehearse.js`, no commits. Keep `node --check` on every JS file,
  `node test_move.js`, `node test_checkpoints.js`, `node verify.js` green.

## Workbook sheets (all dashboard-owned; created on first use like Views/Progress)
- `Dashboard Config` (created by the manager by hand, never by code): `Key | Value`
  rows. Keys used here: `admin` = the admin's sign-in address. The dashboard reads it
  from the downloaded workbook in `load()` into `CONFIG = {admin: "..."}`. If the sheet
  or key is missing, nobody is admin and the add/remove controls are hidden.
- `Dashboard Alerts`: `Job | Email | Added by | When` (text, numberFormat "@", A2:D2000
  preformatted "@" on creation as the Progress sheet does). One row per (Job, Email),
  lower-cased email. Removing = blanking the row (A:D) like `clearAssignment`. Writes go
  through the per-sheet `serialised()` queue in graph.js. Functions in graph.js:
  `ALERTS_SHEET` constant, `ensureAlertsSheet()`, `addAlert(job, email, who)` (upsert,
  no duplicate rows), `removeAlert(job, email)`, exported on `window.CW`. Sheet name is a
  constant, never a parameter.
- `Dashboard Log`: one line per add/remove via `noteChange(job, "Alert", from, to)`:
  add = from "" to the address; remove = from the address to "". (The log is read by
  the dashboard, so addresses appear in the Changes window - that is inside the
  workbook, acceptable.)

## Part A - the dashboard (implementer A)
State: `ALERTS = { [job]: [{email, who, when}] }` read in `load()` from the downloaded
workbook (`Dashboard Alerts`), plus a `PENDA` hold (like `PENDV` in app.js) so an add or
remove shows instantly and survives the ~36 s file lag; drop the hold when the file
agrees or after 180 s.

Admin: `isAdmin()` = `whoAmI().toLowerCase() === (CONFIG.admin || "").toLowerCase()`.
Client-side gating only; say so in a comment.

UI:
1. **Drawer section "Alerts"** under the Comments section, always visible:
   - the addresses subscribed to this job as chips, each with the adder and date in
     small text; if the job is finished (not `blk === sectionIdx("In production")` or
     `j.done`), a line "Finished - no more emails for this job".
   - admin only: an email input (`type=email`, `inputmode=email`, 40 px tall), a
     **Save** button, and a remove "×" on each chip (confirm with a small inline
     "Remove?" / Yes, not `confirm()`). Quick-add chips for addresses already used
     elsewhere in `ALERTS` (so the admin adds a known colleague with one tap).
   - validation: trim, lower-case, must match a simple email pattern, domain must
     equal the admin's domain; otherwise an inline message and no write.
   - non-admin: the chips only, plus "Only the administrator can change alerts."
2. **Header button "Alerts"** (next to Versions) opening a window listing every
   subscription grouped by address: job, customer, section, finished flag, with remove
   buttons for the admin, a count per address, and a note "Emails go out every 3rd day
   at 08:00 to each address listed here, one email per address." (Do not hard-code
   times anywhere else.)
3. **Tick-several-jobs action**: in the existing selection bar (next to "move to…"),
   admin only: "Alert to…" opens a small menu of known addresses plus an input; applies
   `addAlert` to every selected job (serialised, one log line per job).

Writes: optimistic (`PENDA` + re-render) → `CW.addAlert` / `CW.removeAlert` →
`noteChange`. On failure: toast `friendly(e)`, drop the hold, re-render.
`scheduleReconcile()` after a write (exists in app.js).

Tests (`test_alerts.js`, vm-loaded real code like `test_checkpoints.js`): config read
(admin present / missing); admin gating (non-admin never writes even if the function is
called); validation (bad pattern, wrong domain, upper-case normalised); add upsert with no
duplicate row; remove blanks the row; the hold survives a stale parse and is released when
the file agrees; log lines; `ALERTS` never written to localStorage except inside the
`PENDA` hold; finished-job flag. Use fake addresses only (`*@example.test`).

## Part B - the mailer (implementer B) - files under `automation/`
1. `automation/alerts-digest.ts` - an Office Script (`function main(workbook:
   ExcelScript.Workbook): string`). It must:
   - read `Dashboard Config` (admin address = the only allowed recipient domain, same
     rule as the dashboard), `Dashboard Alerts` (A2:D), `Production` (A1:K600 values
     and the header rows), `Dashboard Log` (A2:F).
   - find sections with the same divider rule as `blocksFromValues` in `parser.js`
     (read it; port it exactly: dividers are non-job rows whose text contains
     "customers won't take" / "collect or supply only" / "not sent to floor", the first
     "not sent to floor" = Ready to fit, the second = In production).
   - a job is finished unless it sits in the "In production" section.
   - comments per job: the Production COMMENT column (header text "COMMENT" in row 2),
     the "Notes from Brendan" and "Notes of specials" columns (find by header text,
     not by letter), and Dashboard Log rows where column D = "Comment" (text in F,
     who in B, when in A), newest last. Empty comments are dropped; if a job has no
     comment at all it still appears with "(no comments)".
   - build, per distinct email whose domain equals the admin's domain (skip others,
     they should never exist), a digest of its unfinished jobs: subject
     `"Job alerts: N jobs - <day> <d> <Mon>"` and an HTML body: a short intro line, then
     per job a heading with the job number and a bullet list of comments, then a footer
     link to the dashboard URL (the URL comes from a `dashboardUrl` key in `Dashboard
     Config`, not from code). Addresses with no unfinished jobs get nothing.
   - return `JSON.stringify([{email, subject, html}])`. Never throw on bad rows; skip
     them.
   - Only `ExcelScript` APIs that exist: `getWorksheet`, `getRange`, `getValues`,
     `getUsedRange`. Read whole ranges once; no per-cell loops through the API.
2. `automation/digest-core.js` - the pure logic (sections, comments, digest building)
   as plain JS shared by the script and the test: the `.ts` file must contain the same
   code inline (Office Scripts cannot import), so generate the `.ts` from the core with
   a tiny `automation/build-script.js` (node) and keep them in sync; document that.
3. `automation/test_digest.js` - Node test with an in-memory fake `workbook` (only the
   methods used) covering: sections, finished jobs skipped, comments from all four
   sources, no-comment job, unknown-domain address skipped, address with nothing to
   send omitted, subject count and date formatting, HTML escaping of comment text,
   missing sheets handled without throwing (returns "[]").
4. `automation/SETUP.md` - click-by-click for the admin: Excel on the web → Automate →
   New script → paste `alerts-digest.ts` → save as "Dashboard alerts digest";
   Power Automate → Scheduled cloud flow → Recurrence every 3 Day at 08:00, time zone
   Dublin → Excel Online (Business) "Run script" on the workbook in the ProductionProgress
   site (Location: SharePoint site, Document Library, File, Script) → Parse JSON
   (schema given) → Apply to each → Office 365 Outlook "Send an email (V2)" (To =
   item email, Subject, Body = html, Is HTML = yes) → Save → Test. Include the exact
   Parse JSON schema, how to run a test with "Test → Manually", where to see run
   history, and how to pause the flow. Placeholders only for names/addresses.
